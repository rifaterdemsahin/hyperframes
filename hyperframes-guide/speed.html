⚡ Cloud vs local render speed

How fast is a cloud render compared with rendering on your own computer?

Local is measured. Cloud is not. On this Mac a 20 second 1080p video rendered in about 14 seconds. Hyperframes publishes no timing figures for cloud rendering, and I have not rendered in the cloud, so I give you what the docs say and a clearly labelled model instead of a made-up number. For a video about 3 minutes long, my reasoning says local is already fast enough that cloud saves little or nothing.

1. Local: what I measured

Setup: Apple M1 Max, 10 cores, 64 GB, Hyperframes 0.9.67, npx hyperframes render. Test composition: 20 s, 1920x1080, 30 fps (600 frames), a slowly zooming background image, a headline and three text cards fading in. No video footage, no audio. Measured 18 Nov 2026. Real compositions with footage or heavy effects will be slower.

The real draft, measured

Later the same day I rendered the actual first draft: 3 min 38 s, 1080p, 30 fps, with sound, in about 48 seconds (3 workers on the same Mac), about 4.5x faster than real time. That is faster than the "about 1.5 minutes" scaled estimate above, so treat the estimate as pessimistic. The whole pipeline, including the quality check and a web copy, took about 65 seconds. 2. Cloud: what the docs say

No wall-clock timings are published. These are the documented mechanics.

  • Parallel chunks. On AWS Lambda a workflow runs Plan, then many RenderChunk workers in parallel, then Assemble. By default it uses up to 90% of the account's unreserved Lambda concurrency, at most 256 chunks at once. Cloud Run follows the same plan, chunks, assemble shape.
  • Limits. Each Plan, chunk and Assemble invocation must finish within 15 minutes. Distributed renders are SDR only, 4:2:0 only, and HLS is not offered.
  • Overheads exist. Cold starts, planning, S3 transfer and assembly are fixed costs before any parallel gain. The docs themselves warn that "cloud dispatch adds latency to a fast local loop".
  • HyperFrames Cloud (HeyGen managed). Projects over 200 MB upload media separately; uploads are cached for re-renders. The Free Studio plan includes 5 cloud exports a month.
  • The docs' own advice: stay local while iterating. Use Lambda for "multi-minute videos, 4K masters, or large parallel batches", the work "too long or too large for one host".
  • Cost shape. Lambda bills compute time (GB-seconds) plus a tiny Step Functions fee. The docs show a sample progress line of $0.0214 for one render; treat that as format illustration, not a quote.

3. A model for when cloud wins

This is my illustration with assumed numbers, not a measurement. It assumes cloud workers are as fast as this Mac, which may not be true.

If a render takes L seconds locally, cloud time is roughly O + L / N, where O is the fixed overhead (cold start, plan, upload, assemble, download) and N the chunks running at once. Cloud is faster only when O < L x (1 − 1/N).

Verdict for this video

  • Render locally. A 3 minute 1080p video should take a few minutes on this Mac, with no account, no upload and no cost.
  • Cloud would matter if your computer is much slower than this one, you want a 4K master, you render many versions, or you want to keep working while it renders.
  • Cheap middle path: use --quality draft for review cuts and the default quality only for the final.

Reproduce my test

cd video
npx hyperframes render --quality draft --output out/draft.mp4
npx hyperframes render --quality looks --output out/looks.mp4
npx hyperframes render --quality looks --resolution 4k --output out/4k.mp4

Run each twice and ignore the first (warm-up). To measure cloud yourself, deploy with npx hyperframes lambda deploy and compare lambda render --wait against the local figure for the same project. I can do that if you want to supply AWS or HeyGen credentials, but I would not use credentials unprompted.
