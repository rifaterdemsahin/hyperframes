Instructions for AI coding agents (Claude Code, Codex, Cursor) working in this repo. Humans: start with README.md. This file is reusable: keep it when you copy the repo as a template for the next video.

What this repo is

A video production workspace. It holds the script, a storyboard, a master spec and a Hyperframes project (video/) that renders the MP4, plus a GitHub Pages site that the owner uses to review work and give feedback. Work moves through five stages, shown on the intro page and in the top menu in this order: 1 Plan (Preprod), 2 Build (Prod), 3 Review, 4 Publish (Postprod), 5 Project. The menu and the intro come from spec/menu.json (run node scripts/build-menu.mjs); add a new page there, in the stage where it belongs.

The single source of truth for the current video is script/scenes.json (scenes, voiceover text, timings, overlays) and spec/project.json (brief, rules, acceptance criteria, risks, decisions). Everything on the site that describes the video is generated from those two files.

When the system itself changes (a new script, service or page), update NODES, EDGES and DEPS in scripts/build-architecture.mjs so the hub diagram stays true.

Workflow rules

  1. Commit, push and deploy every change, and say so. The site is GitHub Pages from main at the repo root. After pushing, wait until the live URL serves the new content, then report "committed, pushed, deployed" with the URL. Open the page in Google Chrome (open -a "Google Chrome" <url>).
  2. Version every release. Run node scripts/version.mjs bump ... with a one-line message and the pages that changed. It updates versions.json, the footer data in nav.js, changelog.html and the ?v= cache-busters. Use patch for wording fixes, minor for new content or features, major for a restructure. Release order: bump, run the build scripts, run build-changes-page.mjs (it compares HEAD with the working tree, so it must run before the commit), then commit, push and deploy.
  3. Keep Recommendations current. recommendations.html is hand-written. With each new draft, rescan the project, update it and its data-reviewed-draft; npm test fails when it is more than 2 drafts behind.
  4. Feedback loop. The owner pastes text copied from the copy-feedback bars (the storyboard, the kanban, and the bar on every other page). Implement it, update every related section (script, spec, checklist, recommendations, kanban, hub, README), then release with --clear-notes=<the pages you implemented>. That deletes only those pages' notes from the owner's browser; the version is the only record kept. Never clear notes on pages you did not implement.
  5. Do not touch the owner's browser storage when testing. Browser automation runs in the owner's real Chrome profile, so localStorage on the live site holds their real notes. Test read-only. If a test must write, save the existing value first and put it back. Never call removeItem or clear on a key you did not create.
  6. No secrets in git. The repo is public. FAL_KEY lives only in .env (git-ignored). Run git grep for key prefixes before every commit.
  7. Footer dependencies. Every page footer lists what the page depends on, as links, from deps in versions.json. When you add a page or a new data source, add its deps (page keys link to pages, repo paths to GitHub, http links stay external).
  8. Signal, not noise. When the owner selects an option, hide the ones not selected (collapse them out of the page, keep them in the source file, and reveal them with ?all=1 where it makes sense). Show decided items as decided, not as open. Keep pages and replies to what the owner needs to act on.
  9. State what you did not verify. Say when a number is your estimate, when a source is the vendor's own, and when you did not look at the rendered result.

Content rules

The rules in spec/project.json win. The main ones: no AI-generated text, numbers, documents or screens in images (fal.ai makes text-free mood plates only); real footage for real things; blur personal data at the source; one main call to action; keep the disclaimer; AI is framed as support, not a replacement for the professional. Do not invent links, prices or facts: ask, or mark the item as open in the kanban.

Adding a page

  1. Create the page. Include <script src="nav.js?v=1.0.0"></script> right after <body> (use ../nav.js in a subfolder) and use site.css. The version footer and the copy-feedback bar appear automatically.
  2. Add it to MENU in nav.js and to pages in versions.json.
  3. Run node scripts/version.mjs bump minor "new page" <page>, then commit, push, deploy.

Pages with their own feedback UI set <body data-feedback="custom">.

Hyperframes project notes

  • The project in video/ pins hyperframes@0.9.67. Read the release notes before upgrading.
  • video/index.html is the composition that renders to MP4. Never add the site menu or footer to it.
  • Follow video/CLAUDE.md for the render contract: timed elements need data-start and class="clip", the root timeline is paused and registered on window.__timelines, and only deterministic logic.
  • Always run npm run check, then look at snapshots, before reporting a scene done.
  • Render locally; see the speed page for why cloud rendering rarely pays off at this length.
  • How long a render takes (measured by render-draft.mjs, Apple M1 Max, 10 cores, 5 workers, for a ~4:04 film): about 3 to 3.5 minutes end to end (median 3 min 12 s over the last 5 runs, range 2 min 48 s to 3 min 18 s). Of that, the MP4 render itself is about 2.5 minutes (2 min 10 s to 2 min 32 s), the 720p web copy ~25 s, npm run check ~12 s, frames and site pages under 1 s. Early drafts with lighter scenes took 1 to 2 minutes. Budget about 5 minutes per draft including the look at the frames; plan the background wait instead of polling. The live numbers are on the Renders page (renders.html#render-time), refreshed from spec/performance.json on every render.
  • A render only happens if npm run check passes with 0 errors: render-draft.mjs stops at the check, leaves draft/vN/video.mp4 missing, and the review page falls back to the previous MP4. npm test fails when the latest draft has no MP4. Animate transforms (x, y, xPercent, yPercent, scale, opacity) in GSAP: tweening top, left or right fails the check (gsap_non_transform_motion). To change layout, use an instant tl.set while the element is hidden.

Keynote style (from Draft v11)

script/scenes.json has "style": "keynote". Each scene's keynote array is the screen: one beat per idea, { "at": "<words in the voiceover>", "text": "...", "key": "<accent word>" }, or { "at", "image": "<assets/bg name>", "text", "key" } for a full-bleed image with one short caption. The first beat has no at. Rules: at most 6 words, no lists, one accent word, no boxes, borders, shadows or icons. Text you take off the screen goes to the voiceover, the per-scene HTML comment and video/notes.md (both generated). build-video.mjs warns when a beat is under its reading floor (0.68 s + 0.225 s a word): merge or drop it. Run audit-keynote.mjs before a release; it must report 0 flagged moments. A beat may add "visual": "<name>": a drawn SVG above the line from knVisual() in build-video.mjs (no logos, no screenshots, no text inside the drawing). Music: video/assets/music/ holds the source, LICENSE.md and mix.json; build-video.mjs mounts bed-mix.mp3 as <audio id="music">. Part 1 uses no real footage (owner decision, spec rule set aside). Beats start on the spoken word when video/assets/vo/<id>.transcript.json exists (word timestamps: whisper <clip>.mp3 --model base.en --word_timestamps True --output_format json, converted to {words:[{text,start,end}]}); regenerate it whenever a voice clip changes, then re-run mix-music.mjs. Explain every specialist term in plain words the first time it appears (spec rule, Draft v13).
